# Evaluator 테스트 전략 상세

> skill.md의 Phase 3 Evaluator에서 참조. 작업 유형별 상세 테스트 설계 가이드.

## 테스트 실행 규칙

1. **엔진 데이터로 명확하게 검증** — 실제 엔진 내부 데이터가 의도한 대로 변경되었는지 직접 확인. 프로퍼티 값, 오브젝트 상태, 로그 출력 등 구체적 데이터로 판정
2. **테스트 환경 확인 후 실행** — 테스트 전에 환경(에디터 연결, 에셋 로드, PIE 상태 등)이 갖춰졌는지 먼저 확인. 환경이 안 되면 테스트 실행하지 말고 환경부터 구축
3. **Python으로 검증이 힘든 데이터는 C++ 테스트 코드 작성** — 엔진 내부 상태, 스레드 컨텍스트, 네이티브 자료구조 등 Python API로 접근 불가한 데이터는 C++ 테스트 코드를 직접 작성하여 검증

## 테스트 설계 원칙

### "내 변경이 뭘 바꾸는가?"에서 출발

| 변경 종류 | 테스트가 증명해야 할 것 |
|-----------|------------------------|
| **버그 수정** | 재현 조건에서 더 이상 발생하지 않음 + 기존 동작 보존 |
| **새 기능** | 명세대로 동작 + 기존 시스템과 충돌 없음 |
| **리팩토링** | 외부 동작이 수정 전과 동일 (입출력 보존) |
| **성능 최적화** | 동작 동일 + 측정 가능한 성능 개선 (또는 회귀 없음) |
| **에셋 작업** | 구조 올바름 + 참조 무결 + 에러/경고 없음 |

### 테스트 범위: 수정 반경 기준

```
직접 수정 코드/에셋  →  반드시 테스트
수정에 의존하는 코드  →  영향 범위면 테스트
무관한 코드          →  테스트 불필요
```

- C++ 수정: 수정한 함수를 호출하는 경로 추적 → 영향 범위 파악
- 에셋 수정: `get_asset_references`로 참조 관계 파악

### AC → 테스트 1:1 매핑

Planner가 정의한 각 AC에 최소 하나의 검증. 검증 불가능한 AC → Planner로 돌아가 재정의, 또는 코드 리뷰로 대체.

## 크래시 수정 테스트 전략

**핵심: 버그 재현 조건을 테스트로 인코딩.**

1. **재현 조건 특정** — 크래시가 발생하는 정확한 조건 (입력값, 상태, 시퀀스)
2. **재현 테스트 작성** — `execute_python` 또는 PIE에서 해당 조건 재현
3. **수정 후 통과 확인** — 크래시 없음, 올바른 결과
4. **경계값** — 재현 조건의 변형 (0, max, null, 빈 배열, 동시 접근 등)
5. **회귀 테스트** — 정상 케이스가 깨지지 않았는지

예: 병렬 메쉬 Boolean에서 Triangle 접근 크래시
→ "동일 메쉬 조합으로 Boolean 실행 후 크래시 없이 결과 유효" 테스트

## 최적화 테스트 전략

**핵심: Planner baseline 대비 동작 보존 + 성능 개선.**

1. **동작 보존 (필수)** — Planner에서 수집한 동작 baseline과 비교
   - 같은 입력 → 같은 출력 (또는 허용 오차 이내)
   - 상태 변수, 프로퍼티 값 비교
2. **성능 비교** — baseline 대비 개선 확인
   - 동일 측정 방법으로 재측정, 개선율 계산
   - 에디터: `execute_python` + `time.perf_counter()`
   - PIE: `pie_execute_command("stat unit")` 등
3. **스레드 안전성 (병렬화 시)** — N회 반복 결과 일관성
4. **부하 조건** — 실제 부하(다수 액터, 복잡한 씬)에서도 검증

예: GT→Worker Thread 이동
→ "AnimInstance 프로퍼티 값이 baseline과 동일" + "GT 시간 감소"

## 신규 피쳐 테스트 전략

### 에셋 검증
1. 존재 & 타입 — 에셋 로드, 올바른 클래스
2. 구조 — 컴포넌트, 노드, 파라미터 구성
3. 프로퍼티 값 — 기본값, 설정값 일치
4. 무결성 — `validate_assets` 에러 0건, 참조 정상
5. 컴파일 — BP/머티리얼 컴파일 성공

### 시스템 파이프라인 (CSS, 머티리얼, 애니메이션 등)
1. 입력 조건 설정 → 파이프라인 실행 → 출력 검증
   - 메쉬: 버텍스 수, 섹션 수, UV 채널 수, 바운드
   - 머티리얼: 파라미터, 노드 연결, 컴파일
   - 애니메이션: 노드 연결, LOD, 스테이트 전환
2. 부작용 검증 — 관련 없는 시스템에 영향 없는지

### 런타임 게임플레이 (PIE)
```
play_in_editor(start) → 초기 상태 확인 → 동작 실행 → 결과 확인 → play_in_editor(stop)
```
- 상태 전이: A → 동작 → B 확인
- 경계값: 0, max, 음수 등

### 엔진 레벨 동작
직접 접근 불가한 엔진 내부 → 관찰 가능한 외부 효과로 간접 검증:
- URO 스킵 → AnimInstance 프로퍼티 업데이트 여부
- 캐시 히트/미스 → 연산 시간, 로그 메시지
- 병렬 처리 → 반복 시 결과 일관성

## 테스트 환경 구축 의무

자동 테스트가 어려워 보이는 경우에도 **반드시 코드로 검증 가능한 방법을 고안**한다. 사용자에게 화면 확인이나 수동 테스트를 요청하지 않는다.

| 상황 | 해결 방법 |
|------|-----------|
| 에디터 MCP 미연결 | 에디터를 직접 실행하여 연결 |
| 멀티스레드 타이밍 의존 | 반복 실행 + 결과 일관성 검증, 로그 기반 검증 |
| 특정 빌드 설정에서만 재현 | 해당 빌드로 실행하여 검증 |
| 런타임에서만 확인 가능 | PIE 실행 → `pie_*` 시리즈로 검증 |

**코드 리뷰는 Codex와 함께 수행** (`/codex:rescue`) — 단독 코드 리뷰로 검증 완료 처리하지 않는다.
