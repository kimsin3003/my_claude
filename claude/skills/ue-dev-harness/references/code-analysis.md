# Code Analysis Rules (UserPromptSubmit-hook 강제 점검 대상)

이 파일은 `check-code-analysis.js` hook이 사용자 메시지에서 분석 키워드를 감지하면 강제 로드된다. 본문이 길어도 OK — 분석 작업 시작 시점에 매번 다시 읽힌다.

코드 분석 작업(크래시 원인 분석, 동작 추적, 컨텍스트 수집 등) 수행 시 아래 A1~A4를 모두 적용한다.

---

## A1. 상속 체인은 root와 leaf까지 양방향 추적

C++ virtual 메서드/클래스 동작을 추론할 때, **한 단계만 위/아래** 또는 **직계 부모만** 보고 단정하지 말 것. derived 클래스가 override + super 호출 + 자기 추가 본문을 갖는 **template-method 패턴이 흔하다**.

**절차:**
1. 상속 체인을 **root(인터페이스/추상 베이스)까지, 그리고 leaf(final/구체)까지 모든 단계 빠짐없이** 추적
2. 각 단계마다 그 위/아래에 또 있는지 grep으로 다시 확인하며 반복
3. virtual 메서드 호출 흐름 추적: `grep "::MethodName"`으로 base/모든 derived의 override·정의를 찾고, 각 본문이 super를 호출하는지, 어떤 derived를 호출하는지 모두 확인
4. 함수 이름이 `ExecuteXxx`처럼 어색하게 specialized되어 있으면 "진짜 `Execute`는 어디"를 별도 grep으로 확인 (base의 template-method 신호일 가능성)
5. Explore agent 보고서가 결론을 내리면, 그 결론이 의존하는 **핵심 함수들의 상속 체인은 직접 cpp 펴서 root와 leaf까지 verify**. 보고서 trust 후 그대로 인용 금지.

**Incident (반복 금지):**
CSS의 `FMergeOperation::Execute`가 `FBaseSkinOperation::Execute`(자동 변환)를 super 호출 후 `ExecuteMergeOperation`(자기 본문)을 호출하는 구조였는데, `FBaseSkinOperation::Execute` 본문(변환 없음으로 보이는)만 보고 "RunOperation은 convert 안 한다"로 단정해 사용자에게 잘못된 분석을 보고. 실제로는 derived의 `Execute` override가 변환을 트리거하고 있었다. **상속 체인을 위/아래 끝까지 안 본 결과.**

## A2. 콜스택 → 코드 변수 레벨까지 추적

크래시/버그 콜스택을 받았을 때:

1. 크래시 지점부터 **변수 레벨까지** 추적
2. **함수명만 보고 판단 금지** — 함수 이름이 직관적으로 보여도 본문을 펴서 어떤 분기/상태에서 도달했는지 확인
3. 콜스택의 각 프레임마다 "왜 이 함수가 이 인자로 호출됐는가"를 위 프레임에서 답할 수 있어야 함
4. 어셈블리 레벨 콜스택이면 PDB/심볼로 원본 매핑 시도

---

## A3. 크래시 원인 가설은 양방향 검증

가설을 세웠으면 **다음 두 가지를 모두 설명할 수 있어야** 한다:

1. **재현 조건에서 왜 크래시가 발생하는가** (positive case)
2. **정상 케이스에서 왜 크래시가 발생하지 않는가** (negative case)

한쪽만 설명되면 가설 미완 → 코드로 복귀해서 보강.

**추가 룰:**
- 크래시 발생 조건이 명확하다면, 해당 조건에서만 발생하는 이유를 찾을 것
- 찾은 원인이 **정말 그 조건에서만** 발생할 수 있는 이유가 될 수 있는지 한 번 더 체크 (다른 무관한 조건도 같은 원인으로 크래시 날 수 있다면 가설이 너무 광범위)

---

## A4. 컨텍스트 수집은 변수 레벨까지

신규 피쳐/리팩토링 작업 전 컨텍스트 수집 시:

1. 관련 에셋/코드 탐색 (Glob/Grep)
2. **변수 레벨까지 확인** — 함수 시그니처만 보고 추정 X, 본문 내부의 변수·플래그·상태 변화까지 읽음
3. 핵심 함수는 호출 사이트들도 grep으로 찾아 어떤 맥락에서 불리는지 확인
4. 이미 비슷한 패턴이 코드베이스에 있는지 점검 — 있으면 그 컨벤션 따름

---

## A5. Verify는 끝까지 — 중간 보고로 끊지 말 것

사용자가 "확인해줘"/"verify 필요" 같이 검증을 위임했다면, **추가 확인할 게 없는 상태까지** 진행한 후 한 번에 결론·제안을 보고한다.

**금지:**
- 1차 verify 후 "X도 확인 필요/Y 검증 후 진행" 같은 잔여 verify 항목을 사용자에게 떠넘기는 중간 보고
- "조건부 가능" / "이거 보고 결정해주세요" 식의 결정 의존 미루기

**왜:** 사용자가 verify를 위임한 의도는 결론까지 도달해달라는 것. 중간 핑퐁은 사용자 시간을 빼앗고 컨텍스트도 분산시킨다.

**예외 — 정당한 중간 보고:**
- verify 도중 **사용자만 답할 수 있는 외부 정보**가 필요 (의도, 도메인 지식, 우선순위)
- verify 결과 **명백한 안전상 위험** 발견 → 그 상태에서 즉시 보고
- 작업 범위가 위임 시점보다 N배 커진 게 드러남 → 재합의 필요

**탐지 신호 (자가 점검):**
- 보고서에 "~ 확인 후 진행 가능", "~ verify 필요", "다음 verify 후 진행" 같은 문구가 있으면 → 그 verify를 직접 끝내고 다시 보고
- 결론이 "조건부" 형태로 끝나면 → 조건을 직접 검증해서 무조건부 결론으로

---

## 점검 절차 (hook 발동 시)

1. A1~A4를 모두 읽었는지 확인
2. 분석 작업이 어느 카테고리인지 판단 (크래시: A1+A2+A3, 동작 추적: A1+A2, 피쳐 컨텍스트: A1+A4)
3. 해당 룰을 머릿속에 두고 분석 시작
4. 분석 결론을 사용자에게 보고하기 전, 위 룰 위반 없이 결론에 도달했는지 자가 점검
